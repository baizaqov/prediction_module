# Роли и права доступа (RBAC)

Источники: §2 «Роли модуля», §3.1, §3.2, §3.3, Приложение 3 (п.8), Приложение 4 (столбец «Роль»).
Пометки `[ТРЕБОВАНИЕ] / [ВЫВОД] / [ПРЕДПОЛОЖЕНИЕ] / [ПРОТИВОРЕЧИЕ] / [ПРОБЕЛ]` — см. [overview.md](overview.md).

> **Предупреждение.** В постановке **два независимых источника** распределения факторов между ролями:
> словесные зоны ответственности в §2 и столбец «Роль» в Приложении 4. Они расходятся по **8 категориям из 9**
> (см. §5 ниже). До ответа на `Q-001` матрица «роль → факторы» реализации не подлежит.

# 0. Состояние в существующем коде

Раздел добавлен после изучения репозитория `gisbb-forecast`. Разбор — в
[as-is-gap-analysis.md](../02_TECHNICAL/as-is-gap-analysis.md).

## 0.1 Роли, которые реально существуют

`[ФАКТ · roles.py:11-21]` В системе заведены четыре роли, и **ни одна из них не является ролью
из постановки**:

| Системное имя | Назначение | Права в модуле |
|---|---|---|
| `GISBB_FORECAST_ANALYST` | Профильный аналитик модуля прогнозирования | Чтение и запись |
| `GISBB_SUPER_ADMIN` | Суперадминистратор системы | Чтение и запись |
| `GISBB_NCOZ_ADMIN` | НЦОЗ — общественное здравоохранение | Только чтение |
| `GISBB_MCHS_ADMIN` | МЧС — чрезвычайные ситуации | Только чтение |

Группы прав в коде: `WRITE_ROLES` = аналитик + суперадмин; `READ_ROLES` = они же плюс НЦОЗ и МЧС.

`[ФАКТ]` Ось разграничения принципиально другая: **кто работает с модулем против кто потребляет
результаты**, а не принадлежность к ведомству. Ролей КСЭК, КВКН, МИО и Эксперта гос. органа
в системе нет.

## 0.2 Ограничения платформы

| Ограничение | Источник | Следствие |
|---|---|---|
| Роли ведутся в Keycloak realm, он объявлен единственным источником истины; экспорт вручную не править | `roles.py:6-7` | Четыре роли ПЗ должен завести администратор платформы. Сервис их только читает |
| Список ролей продублирован во фронтенде (`forecast.roles.ts`) | `roles.py:5` | Изменение набора ролей требует синхронной правки фронтенда |
| «Слой прав в платформе упразднён», авторизация только по ролям | `security.py:6` | Тонкой настройки прав вне ролей не существует; всё разграничение придётся выражать ролями |
| В токене передаются только сведения об организации: `user_id`, `org_id`, `org_name`, `org_bin`, `full_name` | `security.py:22-27` | **Территории в токене нет** — территориальное ограничение (`Q-011`) реализовать нечем |

## 0.3 Как разграничение устроено сейчас

`[ФАКТ · routers/risk.py:51,59,68,78]` Проверка прав выполняется на уровне эндпоинта и только грубо:

| Эндпоинт | Требуемые роли |
|---|---|
| `GET /v1/risk/infections` | READ |
| `GET /v1/risk/infections/{code}/factors` | READ |
| `POST /v1/risk/assessments/preview` | READ |
| `POST /v1/risk/assessments` | WRITE |

**Ролевого разграничения факторов нет.** Каталог фильтруется только по панели
(`service.py:22-28`). Любой пользователь с ролью на запись может выставить балл по любому из 46 факторов.
Требование §3.2 «попытка передать балл по фактору вне зоны ответственности должна отклоняться сервером»
не реализовано.

`[ПРОТИВОРЕЧИЕ]` Расходится и с Приложением 4: фактор №20 в приложении закреплён за КСЭК,

## 4. Требуемые пунктом задания разрезы, отсутствующие в постановке

Задание требует зафиксировать по каждой роли ЭЦП-действия и маршруты передачи документов.
`[ПРОБЕЛ]` **В постановке этих сущностей нет.** Ниже — честная фиксация отсутствия, а не проектное решение.

| Роль | Действия, требующие ЭЦП | Кому может отправлять документ | От кого может получать документ |
|---|---|---|---|
| `ROLE_EXPERT` | **Не определено — ЭЦП в постановке не упоминается** (`Q-021`) | **Маршрутизации документов в постановке нет** (`Q-024`) | **Маршрутизации документов в постановке нет** (`Q-024`) |

| `ROLE_MIO` | Не определено (`Q-021`) | Нет (`Q-024`) | Нет (`Q-024`) |

## 6. Технические следствия для реализации `[ВЫВОД]`

1. **Авторизация на двух уровнях.** Роль определяет (а) видимость записей журнала и (б) множество факторов,
   допустимых к вводу. Второй уровень обязан проверяться на сервере при сохранении каждого балла (§3.2).
2. **Матрица «роль → факторы» должна быть данными, а не кодом.** Она задаётся столбцом «Роль» в каталоге
   факторов и, следовательно, меняется вместе со справочником; хардкод распределения недопустим.
3. **Правка весов — отдельное право**, не выводимое из «зоны ответственности»: принадлежит только `ROLE_EXPERT`.
4. **Отсутствие факторов у Эксперта** делает для него страницу калькулятора пустой. Пока `Q-007` не закрыт,
   поведение кнопки «Оценить риск» для Эксперта не определено.
5. **Множественность ролей у пользователя** постановкой не рассматривается (может ли один аккаунт иметь две роли) —
   см. `Q-044`.
