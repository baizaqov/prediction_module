Разбор репозитория `gisbb-forecast` относительно требований ПЗ «Оценка риска».
Документ отвечает на три вопроса: что уже сделано, чего нет, и где код расходится с постановкой.

| Параметр | Значение |

| Разобранная ветка | `origin/test`, коммит `bff4e0b` «Risk level added» |
| Другие ветки | `origin/demo` (на один коммит позади), `origin/main` (**только README, кода нет**) |
| Объём | ~2 800 строк Python |
| Дата разбора | 11.08.2026 |

> Ссылки вида `scoring.py:62` указывают файл и строку в ветке `origin/test`.

## 1. Что это за сервис

`gisbb-forecast` — микросервис платформы ГИС ББ, реализация п. 4.10.6 ТЗ
«Прогнозирование и оценка биологических рисков». Единственный не-JVM сервис платформы.

| Аспект | Как устроено |
|---|---|
| Стек | Python 3.12, FastAPI, SQLAlchemy, scikit-learn, Pydantic |
| Размещение | За общим шлюзом, маршрут `Path=/api/forecast/**`, `StripPrefix=2` |
| Обнаружение | Eureka, `py-eureka-client`, требуется `EUREKA_ENABLED=true` в кластере |
| Аутентификация | Внутренний JWT в заголовке `X-Internal-Authorization`, HS256, общий секрет `gisbb.internal-token.secret` (`security.py`) |
| Авторизация | Только по ролям из claim `roles`. В комментарии `security.py:6` зафиксировано: «слой прав в платформе упразднён» |
| Источник ролей | Keycloak realm. `roles.py:6` — «realm источник истины, экспорт вручную не править» |
| Хранилище | PostgreSQL, общая `gisbb_db`. Две схемы: `forecast` (прогнозирование) и `bb_risk` (оценка рисков) |
| Миграции | Пока нет: `create_all` при старте с ретраями, затем идемпотентный сид (`db.py: init_db`). Alembic заявлен как «что дальше» |
| Конфигурация | Переменные окружения, общий `gisbb-config`/`gisbb-secret`, как у Java-сервисов |

**Вывод для планирования.** ПЗ описывает не новый проект, а **доработку существующего сервиса**.
Каркас, схема БД, аутентификация, шлюз, CI и деплой уже есть.

### 1.1 Ветки и деплой

Весь модуль оценки риска пришёл **одним коммитом** `bff4e0b` «Risk level added» от 24.07.2026,
и он есть **только в `test`**. Ветки не разошлись: `test` = `demo` + этот коммит.

| Ветка | Состояние | Что делает CI при push |
|---|---|---|
| `test` | Модуль оценки риска есть | Сборка образа + **автоматический деплой** на тестовый контур |
| `demo` | Модуля оценки риска **нет** — ни `app/risk/`, ни каталогов, ни движка | Сборка образа + **автоматический деплой** на демо-контур (namespace `demo`) |
| `main` | Только README, кода нет | Job `release`, вручную |
| теги | — | Деплой на прод, вручную |

**База для доработки — `origin/test`.** Брать что-либо из `demo` не нужно: там нет предмета работы.

**Работать следует в фиче-ветке.** Пуш в `test` не просто собирает образ, а сразу раскатывает его
на среду, поэтому незавершённая работа окажется в рабочем контуре.

> `main` трогать нельзя: job `release` запускает `mvn release:prepare` — Maven на Python-проекте.
> Это наследие Java-шаблона платформы, работать оно не будет.

**Требует подтверждения tech lead:** принят ли merge request в `test` или пуш напрямую;
нужно ли поддерживать `demo` в актуальном состоянии — сейчас демо-контур работает без модуля оценки риска.

### 2.1 Что именно готово в расчёте

`risk/scoring.py` — порт поставочного `reference/scoring.py`, совпадает с JS-двойником
`reference/scoring.js`, проверяется 16 тест-векторами с точностью 1e-6
(`tests/risk_test_vectors.json`, `tests/test_risk_scoring.py`).

| Требование ПЗ | Реализация |
|---|---|
| `интегральный_индекс = SUM(балл × вес) / N_оценённых` | `scoring.py:144` |
| `полнота = N_оценённых / N_панели` | `scoring.py:145` |
| `индекс_с_поправкой = индекс × (0,5 + 0,5 × полнота)` | `scoring.py:146-147` |
| Пороги 3 / 5 / 7 | `scoring.py:27`, `compute_level` — `scoring.py:56-68` |
| Красный триггер при балле ≥ 3 переопределяет уровень | `scoring.py:30, 57-59, 130` |
| Балл 0–4, вес 1–4 | `scoring.py:32-33, 111-124` |
| Незаполненные факторы не участвуют в расчёте | `scoring.py:102-104` |
| Расчёт исключительно на сервере | Движок без внешних зависимостей, вызывается только из `service.assess` |

Сверх ПЗ движок возвращает разрезы `by_category` и `by_factor_class`,
а также `validate_catalog` — проверку каталога на целостность (`scoring.py:174-207`).

### 2.2 Существующий API

Префикс `/v1/risk`, под шлюзом — `/api/forecast/v1/risk`.

| Метод | Путь | Роли | Назначение |
|---|---|---|---|
| GET | `/infections` | READ | Список ООИ с факторной оценкой |
| GET | `/infections/{code}/factors?panel=` | READ | Каталог факторов по панели |
| GET | `/assessments` | READ | Список сохранённых оценок с фильтрами и пагинацией (T-10) |
| POST | `/assessments/preview` | READ | Расчёт без сохранения (интерактивный калькулятор) |

**Список сохранённых оценок есть (T-10).** Уровень и признак триггера пересчитываются
по сохранённым баллам и текущему каталогу при каждом чтении, не хранятся.

## 4. Расхождения кода и постановки

Семь пунктов. Для каждого — что требует ПЗ, что в коде, кто решает и что делать.

### GAP-01 · Ролей из постановки не существует

| | |
|---|---|
| **ПЗ требует** | Четыре роли: Эксперт гос. органа, КСЭК, КВКН, МИО (§2) |
| **В коде** | Четыре совсем другие роли (`roles.py:11-21`): `GISBB_FORECAST_ANALYST`, `GISBB_SUPER_ADMIN`, `GISBB_NCOZ_ADMIN` (НЦОЗ), `GISBB_MCHS_ADMIN` (МЧС) |
| **Суть** | Ось разграничения другая: аналитик / администратор / потребитель результатов, а не по ведомствам. Ролей КСЭК, КВКН, МИО и Эксперта в системе нет вообще |
| **Ограничение** | Роли заводятся в Keycloak realm, который объявлен источником истины (`roles.py:6`). Сервис только читает их из claim `roles` |
| **Кто решает** | Бизнес-аналитик (какие роли нужны) + администратор платформы (завести в Keycloak) + согласование с фронтендом (`forecast.roles.ts`) |
| **Что делать** | Реализовать ролевую модель ПЗ **невозможно**, пока роли не заведены. Запускать этот процесс нужно первым — он самый долгий |

### GAP-02 · Ролевого разграничения факторов нет, а `responsible` для него непригоден

| | |
|---|---|
| **ПЗ требует** | Каждый орган заполняет только свои факторы; попытка внести чужой отклоняется сервером (§3.2) |
| **В коде** | Разграничения нет. Каталог фильтруется только по панели (`service.py:22-28`). Роли на эндпоинтах — грубые: READ на чтение, WRITE на запись (`routers/risk.py:51,59,68,78`) |
| **Поле `responsible`** | Существует (`models.py:62`), но это свободный текст: 21 различное значение на 46 факторов, у факторов 25, 45, 46 — пустое |
| **Суть проблемы** | Появился **третий** источник распределения ответственности, и он расходится с обоими предыдущими. Примеры: №26–44 — «Территориальные подразделения государственного органа в сфере санитарно-эпидемиологического благополучия» (по смыслу КСЭК); №21–24 — «Владельцы (КХ, ЛПХ, ТОО) МИО»; №20 в коде — ветслужбы и акиматы, а в Приложении 4 — КСЭК |
| **Кто решает** | Методолог и бизнес-аналитик |
| **Что делать** | Нужна машиночитаемая привязка «фактор → роль» в каталоге. Текущее поле `responsible` сохранить как справочное, добавить отдельное. См. `Q-001` |

### GAP-03 · У бруцеллёза не размечены панели

| | |
|---|---|
| **ПЗ требует** | Панель — обязательное поле, три значения: Базовая / Расширенная / Полная (Приложение 2, п.4) |
| **В коде** | Механизм панелей есть (`tier`), но **все 46 факторов бруцеллёза помечены `basic`**, `extended` пуст |
| **Дополнительно** | `select_panel` для `extended` возвращает **только** факторы с `tier == 'extended'`, а не basic + extended (`scoring.py:49-52`). Панели не вложенные, а взаимоисключающие |
| **Последствие** | Для пилотной нозологии панель «Расширенная» вернёт пустой список: полнота 0, индекс `None`, уровень «не оценено». Панели «Базовая» и «Полная» дают одинаковый результат — все 46 факторов |
| **У других нозологий** | Разметка есть: чума 50/63, туберкулёз 47/32, ККГЛ 20/33 |
| **Кто решает** | Методолог |
| **Что делать** | Получить разметку 46 факторов по панелям. Отдельно уточнить, вложенные панели или взаимоисключающие. См. `Q-004` |

### GAP-06 · Расчётные величины не сохраняются

| | |
|---|---|
| **ПЗ требует** | В журнале отображается уровень риска последней сохранённой оценки (Приложение 1, п.6) |
| **В коде** | В `assessment` сохраняются только контекст и баллы (`models.py:66-88`). Индекс, полнота, уровень и признак триггера **не персистятся** — они лишь возвращаются в ответе (`service.py:78-98`) |
| **Последствие** | Уровень придётся пересчитывать при каждом чтении по **актуальным** весам. Это де-факто вариант B вопроса `Q-012`: при правке веса Экспертом исторические уровни изменятся задним числом |
| **Оценка** | Похоже, это не осознанное решение, а следствие того, что журнал ещё не делали |
| **Кто решает** | Бизнес-аналитик (`Q-012`, `Q-039`) |
| **Что делать** | Решить до реализации журнала. Хранение рассчитанных величин рядом с оценкой безвредно при любом варианте и нужно журналу для производительности |

### GAP-07 · Территориального ограничения доступа реализовать нечем

| | |
|---|---|
| **ПЗ требует** | Каждый орган видит журнал только по своей зоне ответственности (§3.1) |
| **В коде** | В токене передаётся `UserInfo`: `user_id`, `org_id`, `org_name`, `org_bin`, `full_name` (`security.py:22-27`). **Территории в токене нет** |

| **Кто решает** | Платформенная команда (доработка токена) либо архитектор (отдельный справочник «пользователь → территория» внутри сервиса) |
| **Что делать** | Поднять вопрос до проектирования журнала. См. `Q-011` |

## 9. Две ловушки, которые сработают при первой же доработке

### Ловушка 1 · Схема БД не мигрируется

При старте выполняется `create_all` (`db.py: init_db`), который создаёт **недостающие** таблицы,
но **не изменяет существующие**. Alembic заявлен в README как «что дальше» и не внедрён.

**Последствие.** Изменение модели — период двумя датами (GAP-04), территория двумя уровнями (GAP-05),
сохранение расчётных величин (GAP-06) — на уже развёрнутом контуре не применится. Таблица
`bb_risk.assessment` останется прежней, а приложение либо упадёт при обращении к отсутствующей колонке,
либо будет молча её игнорировать.

**Что делать.** Решить до первого вливания в `test`: внедрять Alembic либо пересоздавать таблицы,
пока реальных данных нет. Второе допустимо только при подтверждении, что сохранённых оценок
на контурах нет.

### Ловушка 2 · Сид каталога не перезальёт изменения

Каталог перезаписывается, **только если число факторов в БД разошлось с числом в файле**
(`catalog_loader.py:67-71`):

```
existing = session.query(Factor).filter(Factor.infection_code == code).count()
if existing == len(factors):
    continue  # уже загружено, данные не изменились
```

**Последствие.** Когда методолог даст разметку панелей (GAP-03) и в `brucellosis.json` будут
проставлены значения `tier`, число факторов останется прежним — 46. Сид сравнит количества,
увидит совпадение и **молча пропустит обновление**. Новая разметка на среду не попадёт.
То же произойдёт при добавлении привязки «фактор → орган» (GAP-02) и при исправлении формулировок.

**Что делать.** Изменить условие перезагрузки: сравнивать не количество, а содержимое —
например по контрольной сумме файла каталога или по версии в реестре нозологий.

> Обе ловушки не зависят от ответов бизнес-аналитика и должны быть закрыты до первого
> вливания в `test`.
