на одной постановке и утверждала, что внешних интеграций нет. Это оказалось верно только
в отношении текста ПЗ: сама платформа — интеграционная, и сервис в неё уже встроен.

Разбор кода — [as-is-gap-analysis.md](as-is-gap-analysis.md).

# Часть A. Интеграции, которые уже работают

## I-1. Шлюз платформы

Сервис доступен снаружи только через общий шлюз: маршрут `Path=/api/forecast/**` →
`lb://gisbb-forecast`, `StripPrefix=2`. FastAPI знает о префиксе через `root_path`
(`main.py: GATEWAY_PREFIX`), поэтому Swagger и ссылки OpenAPI работают корректно.

**Следствие для доработки.** Все новые эндпоинты раздела «Оценка риска» автоматически окажутся
под `/api/forecast/v1/risk/**`. Отдельной регистрации маршрутов не требуется.

Исключение — health-проверка: она смонтирована без префикса, Eureka обращается к инстансу напрямую.

## I-2. Реестр сервисов Eureka

Регистрация через `py-eureka-client` (`app/eureka.py`), запускается в lifespan приложения.
В кластере обязателен `EUREKA_ENABLED=true`, иначе маршрут шлюза `lb://gisbb-forecast` не разрешится.
Зона реестра — из `EUREKA_DEFAULT_ZONE` либо платформенного `EUREKA_CLIENT_SERVICEURL_DEFAULTZONE`.

**Следствие для доработки.** Ничего делать не нужно, но при локальном запуске Eureka отключают.

## I-3. Аутентификация и роли

| Аспект | Как устроено |
|---|---|
| Транспорт | Заголовок `X-Internal-Authorization`, формат `Bearer <jwt>` |
| Алгоритм | HS256, общий секрет `gisbb.internal-token.secret` |
| Что читается | Claim `roles` (верхний регистр, без префикса `ROLE_`) и `userInfo` |
| Состав `userInfo` | `userId`, `orgId`, `orgName`, `orgBin`, `fullName` |
| Проверка | `app/security.py`, зависимость `require_roles(*allowed)` |
| Отказ | 401 при отсутствии или невалидности токена, 403 при недостатке прав |
| Отключение | Флаг конфигурации — при выключенной проверке доступ открыт (локальная разработка) |

`[ФАКТ]` Источник ролей — Keycloak realm, объявленный единственным источником истины.
Список ролей продублирован во фронтенде.

`[ОГРАНИЧЕНИЕ]` В токене **нет территории**. Это блокирует территориальное разграничение
доступа, которого требует §3.1 постановки. См. `Q-011`, `BA-04`.

`[ОГРАНИЧЕНИЕ]` В комментарии `security.py:6` зафиксировано: «слой прав в платформе упразднён,
авторизация только по ролям». Тонкой настройки прав помимо ролей не существует.

## I-4. Общая база данных

PostgreSQL, общая база `gisbb_db`. Сервис владеет двумя схемами:

| Схема | Назначение | Метаданные |
|---|---|---|
| `forecast` | Прогнозирование, климат, прогоны моделей | `app/models.py` |
| `bb_risk` | Оценка рисков: инфекции, факторы, оценки, баллы | `app/risk/models.py` |

Разрешение адреса БД по приоритету: явный `DATABASE_URL` → платформенный `SPRING_DATASOURCE_URL`
с учётными данными из общего `gisbb-config`/`gisbb-secret` (JDBC автоматически конвертируется
в `postgresql+psycopg://…`) → localhost.

Схемы и таблицы создаются на старте: `CREATE SCHEMA IF NOT EXISTS` плюс `create_all` с ретраями,
затем сид каталогов (`db.py: init_db`).

`[РИСК]` **Миграций нет.** `create_all` не изменяет существующие таблицы. Alembic заявлен
в README как «что дальше», но не внедрён. Подробно — раздел 9 в
[as-is-gap-analysis.md](as-is-gap-analysis.md).

## I-5. Климатические данные Казгидромета

| Аспект | Состояние |
|---|---|
| Реализация | `app/integrations/kazhydromet.py` — **заглушка**, данные генерируются синтетически с сезонной структурой |
| Метка источника | `KAZHYDROMET_STUB` |
| Формат записи | `region_code`, `period`, `temp_c`, `humidity`, `precip_mm`, `source` |
| Боевой канал | **через ШЭП**, по образцу `elicense-client` — указано в комментарии к модулю |
| Интерфейс | Стабилен: при появлении боевого канала заменяется только реализация `fetch` |

`[ВЫВОД]` Это единственный пример внешней интеграции в сервисе, и он показывает принятый
в платформе способ получения ведомственных данных — **ШЭП**. Для вопроса об источниках данных
по факторам риска (`Q-051`) это готовый механизм: спрашивать нужно не «возможны ли интеграции»,
а «какие ведомственные системы и по каким факторам должны стать источниками».

К разделу «Оценка риска» климатические данные отношения не имеют: ни один из 46 факторов
бруцеллёза не использует метеопоказатели, а прогнозирование из объёма ПЗ исключено.

## I-6. Эталонный каталог факторов

Внесистемная передача: каталоги лежат в репозитории как файлы `app/risk/data/<code>.json`
и загружаются в БД идемпотентным сидом при старте (`app/risk/catalog_loader.py`).

Загружено 13 нозологий. Каталог бруцеллёза полностью совпадает с Приложением 4 постановки.

`[РИСК]` Сид перезаписывает каталог, только если разошлось **число** факторов. Изменения внутри
файла при неизменном количестве записей на среду не попадут. Подробно — раздел 9 в
[as-is-gap-analysis.md](as-is-gap-analysis.md).

Открытые аспекты: дословная загрузка формулировок с опечатками (`Q-041`), правка каталога
помимо весов (`Q-043`), порядок поставки новых версий (`Q-048`), разметка панелей (`Q-004`).

# Часть B. Чего нет ни в постановке, ни в коде

## I-7. Источник фактических данных по факторам риска

`[ПРОБЕЛ · критический]` Ни постановка, ни код не отвечают, откуда берутся величины,
по которым выставляется балл. 15 факторов из 46 требуют измеримых значений: число больных животных,
охват диагностическими исследованиями, доля привитых, доля абортов, укомплектованность ветслужбы,
число непереданных отчётов, время до изоляции, заболеваемость людей.

Механизм для получения таких данных в платформе есть — ШЭП (см. I-5). Вопрос в том,
какие системы должны стать источниками. См. `Q-051`, `BA-34`.

## I-8. Справочники нозологий и территорий

| Справочник | Состояние |
|---|---|
| Нозологии | Реализован: таблица `bb_risk.infection`, наполняется из `infections.json` |
| Территории | **Отдельной таблицы нет.** В оценке хранится `region_code: String(16)` с пометкой «КАТО региона/района» |

`[ФАКТ]` Классификатор определился — КАТО. Это закрывает часть `Q-020`.

`[ПРОБЕЛ]` Разделения на регион и район нет, справочника территорий как сущности нет,
владелец справочника не определён. Постановка требует два уровня плюс вариант
«Обобщённо по региону». См. `Q-020`, `BA-17`, GAP-05.

## I-9. Передача результатов смежным разделам

`[ПРОБЕЛ]` Разделы «Мониторинг», «Карта», «Устранение», «Отчёт» и прогнозирование по назначению
потребляют уровень риска и факт срабатывания красного триггера, но контракта выдачи нет
ни в постановке, ни в коде. См. `Q-052`, `BA-35`.

## I-10 … I-15. ЭЦП, PDF, уведомления, маршрутизация, вложения, фоновые задания

`[ПРОБЕЛ]` Отсутствуют полностью — и в постановке, и в реализации. Ни одной точки расширения
под них в коде не заложено.

| Тема | Вопрос | Что делать сейчас |
|---|---|---|
| ЭЦП | `Q-021` | Не реализовывать. Учитывать, что подписанные данные должны быть неизменяемыми — влияет на `Q-012` и `Q-013` |
| PDF и выгрузки | `Q-022` | Не реализовывать |
| Уведомления | `Q-023` | Не реализовывать. Потребность косвенно вытекает из периодичности заполнения и критичности красного триггера |
| Маршрутизация между органами | `Q-024` | Не реализовывать. Модель в коде — параллельный независимый сбор данных, что соответствует постановке |

| Фоновые задания | `Q-026` | Планировщика и очереди в сервисе нет. Потребность возникает только как следствие ответов на `Q-009`, `Q-012`, `Q-023` |

## Итог

**Платформенные интеграции реализованы полностью**: шлюз, реестр сервисов, аутентификация с ролями,
общая база. Дорабатывать их для раздела «Оценка риска» не требуется — новые эндпоинты встраиваются
в существующий контур автоматически.

**Внешних интеграций данных нет ни одной**, кроме заглушки Казгидромета. При этом механизм
для них в платформе определён — ШЭП.

Зависимости, требующие решения до начала работ:

| Зависимость | Вопрос | Последствие отсутствия ответа |
|---|---|---|
| Состав ролей в Keycloak | `Q-053` | Ролевую модель ПЗ не на чем реализовать |
| Территория в токене | `Q-011` | Территориальное разграничение доступа реализовать нечем |
| Источник данных по факторам | `Q-051` | Неизвестно, нужен ли интеграционный слой |
| Разделение регион/район | `Q-020` | Модель территории не соответствует ПЗ |
| Получатели результатов | `Q-052` | Возможна переработка при подключении смежных разделов |
