# gisbb-forecast — правила работы в репозитории

Микросервис ГИС ББ «Прогнозирование и оценка биологических рисков» (п. 4.10.6 ТЗ).
Единственный не-JVM сервис платформы. Текущие работы — раздел «Оценка риска» (`app/risk/`).

---

## Стек

Python 3.12 · FastAPI · SQLAlchemy · Pydantic · scikit-learn · PostgreSQL.

За общим шлюзом на префиксе `/api/forecast/**` (`StripPrefix=2`, FastAPI знает через `root_path`).
Регистрация в Eureka. Аутентификация — внутренний JWT в заголовке `X-Internal-Authorization` (HS256),
роли из Keycloak в claim `roles`. Две схемы БД: `forecast` (прогнозирование) и `bb_risk` (оценка рисков).

```bash
uvicorn app.main:app --port 8100    # локально
pytest -q                            # тесты идут на SQLite
```

---

## Конвенции — то, что не угадать

- **ORM в `snake_case`, Pydantic-схемы в `camelCase`.** См. `app/risk/schemas.py`: `infectionCode`,
  `regionCode`, `nameRu`. Не приводить к единому виду — это контракт API.
- **Докстринги и комментарии на русском**, как во всём коде.
- **Ошибки через `ForecastError`** из `app/errors.py`, не голый `HTTPException`.
  Формат тела единый (`error_body`); 403 — нет прав, 422 — валидация.
- **Типы БД переносимые**: `JSON`, а не `JSONB`; `autoincrement`, а не `BIGSERIAL`.
  Тесты идут на SQLite, где схема `bb_risk` не применяется (`app/risk/models.py:18`).
- **Схему менять только миграцией.** `create_all` не изменяет существующие таблицы.

## Не трогать

| Что | Почему |
|---|---|
| `app/risk/scoring.py` | Порт поставочного эталона методолога, совпадает с его же JS-версией. Покрыт 16 тест-векторами с точностью 1e-6. Формула деления на число оценённых, а не на сумму весов — так и задумано |
| `app/risk/data/*.json` | Эталонные каталоги. Опечатки в формулировках намеренные, вопрос об исправлении открыт |
| `app/roles.py` | Роли ведутся в Keycloak realm, он источник истины. Добавлять роли в код бессмысленно |
| ветка `main` | Там job `release` с `mvn release:prepare` — наследие Java-шаблона, на Python не работает |

## Ветки

Два remote, поток строго однонаправленный: **`github` → `GitLab`**.

- `github` (`github.com/MaulenUser/prediction_module`) — совместная работа. Сюда пушатся
  фиче-ветки, сюда же открываются PR. Работать в фиче-ветке от `github/test`, вливать
  готовыми кусками обратно в `github/test`.
- `origin` (GitLab, `gitlab.ezdrav.kz`) — только деплой. **Пуш в `origin/test` или
  `origin/demo` автоматически раскатывает образ на контур** (`deploy-test` в
  `.gitlab-ci.yml`). Свои фиче-ветки и PR сюда не пушить.

Перенос `github/test → origin/test` — осознанное действие владельца репозитория
(`git fetch github && git merge --ff-only github/test && git push origin test`), это и
есть момент деплоя на тестовый контур. Ревью PR на GitHub — единственный барьер перед ним.

`demo` — демо-контур на GitLab, модуля оценки риска там нет. `main` есть только на
GitLab (только README + унаследованный job `release`, см. «Не трогать»); на GitHub
отдельного `main` нет.

## Две ловушки

**1. Миграции есть (Alembic, T-03).** `create_all` в `init_db()` при старте по-прежнему
создаёт недостающие таблицы на новом окружении — это не убрано, но больше не источник
истины для эволюции схемы. Любое изменение `app/models.py` или `app/risk/models.py`
сопровождается миграцией в том же коммите:

1. Поменять модель.
2. `alembic revision --autogenerate -m "..."`, открыть файл и посмотреть глазами —
   `include_name`/`include_object` в `alembic/env.py` уже отсекают чужие схемы
   Java-сервисов (в итоговой миграции должны быть только объекты `forecast`/`bb_risk`),
   но автогенерацию всё равно не применять не глядя.
3. Применить. Процедура зависит от того, что уже на контуре — **не путать**:
   пустая БД → `alembic upgrade head`; БД, где таблицы уже созданы старым `create_all`
   (до Alembic) → без применения самой миграции, один раз `alembic stamp head`.
   Обе процедуры — в README, раздел «Миграции».

`alembic_version` — в схеме `forecast` (`version_table_schema` в `alembic/env.py`), не в
`public`, чтобы не столкнуться с чужими объектами. URL берётся из
`app.config.get_settings().sqlalchemy_url` — та же цепочка источников, что у сервиса,
захардкоженного URL в `alembic.ini` нет. Тесты на SQLite миграции не запускают: там схемы
не применяются, путь через `create_all` для тестов сохранён как был.

**Открытый вопрос:** где именно в процессе деплоя запускать `alembic upgrade head` —
не решено в рамках T-03, это к тех лиду.

**2. Сид каталога не перезаливает изменения.** В `app/risk/catalog_loader.py:67-71` каталог
обновляется, только если разошлось **число** факторов. Правка содержимого при неизменном количестве
записей молча игнорируется.

## Каталог бруцеллёза — контрольные суммы

46 факторов · сумма весов 123 · 9 категорий · 15 `numeric` / 31 `binary` ·
красные триггеры № 17, 18, 21, 24, 31 · числовые № 1–10, 26–29, 45.

Совпадает с Приложением 4 постановки. Все 46 факторов помечены `tier: basic`, панель `extended` пуста.

## Принятые решения бизнес-аналитика

Реализовывать по ним, не переспрашивать.

| Тема | Решение |
|---|---|
| Чья оценка | **Общая на территорию.** Три органа вносят свои факторы в одну запись, индекс по накопленным |
| Строка журнала | **Ожидаемый объект наблюдения**, не сохранённая оценка. Уровень без данных — «не оценено» |
| Эксперт гос. органа | Доступ ко всему: любые факторы, изменение весов, редактирование любых данных |
| Ввод данных | **Вручную.** Балл выставляется по шкале из Приложения 4. У бинарных факторов только 0 и 4 |
| Веса и история | При сохранении оценки фиксируется **снимок весов**. Прошлые оценки неизменны, новые считаются по новым весам |
| Исправление оценки | Разрешено, с историей изменений: дата, значение до и после |
| Роли по факторам | **Временно** по Приложению 4: КСЭК 20, КВКН 13, МИО 13, Эксперт без закрепления |
| Сводная БД | Хранилище весов и прошлых оценок — видеть, по какому весу считали раньше |

**Матрицу «фактор → орган» проектировать как связь многие-ко-многим**, хотя сегодня одна строка
на фактор: методологи указывают несколько ответственных органов. Существующее поле `responsible`
(свободный текст методолога) не трогать, привязку добавлять отдельно.

## Не решено — не угадывать

| Что | У кого ответ |
|---|---|
| Окончательная матрица «фактор → орган»; какой каталог рабочий (46 или 16 факторов) | Методологи, собрание |
| Список обязательных и дополнительных факторов (панели) | Методологи |
| Как сводить недельные, месячные и квартальные данные в одну оценку | Методолог |
| Роли КСЭК, КВКН, МИО, Эксперт **не заведены в Keycloak** | Администратор платформы |

**Правило:** наткнулся на неопределённость — остановись и спроси. Не выбирай вариант сам.
В `docs/01_PRODUCT/open-questions.md` перечислены открытые вопросы; часть из них блокирующие,
и правдоподобное решение «по своему разумению» будет незаметно до приёмки.

Отдельно: проверку «этот орган не имеет права на этот фактор» писать можно как чистую функцию
с тестами, но применять к живым пользователям нельзя — ролей в Keycloak нет.

## Текущее состояние раздела «Оценка риска»

**Готово:** движок расчёта, каталоги 13 нозологий, идемпотентный сид,
`GET /v1/risk/infections`, `GET /v1/risk/infections/{code}/factors`,
`GET /v1/risk/assessments` (T-10), `POST /v1/risk/assessments/preview`, `POST /v1/risk/assessments`.

**Нет:** ролевого разграничения факторов, правки весов и истории, сводной БД, демо-данных.
